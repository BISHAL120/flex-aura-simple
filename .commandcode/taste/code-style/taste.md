# Code Style

- Prefers component-based architecture, splitting the UI into one component per section/feature (and reusing shared pieces like a container, page shell, product card, section heading). Calls this their usual way of working. Confidence: 0.8
- Prefers using CSS variables and design tokens for theme values (colors, border-radius scale, etc.) defined centrally in the global CSS rather than hard-coded values inline in components. Confidence: 0.8
- Values semantic, honest copy over marketing fluff in UI (e.g., replacing "Your payment details are encrypted and secure" with "This is a demo checkout — no payment is processed or stored"). Confidence: 0.7
- Wants website content (product images, names/descriptions, business identity) grounded in the real business and actual products — e.g., swapping generic/placeholder product images for the user's real local photos and rewriting the whole site around what the business actually sells (laser-cut metal art, car logos, custom designs, custom sizes) rather than keeping demo content. Confidence: 0.7
- When rebranding/customizing a site, wants the change applied consistently across every surface — homepage, all pages, metadata, nav links, footer, contact details, cart/checkout/confirmation copy — with all stale placeholder references (old brands, Unsplash URLs, fake addresses/emails, demo categories) actively searched for and removed, not just the visible homepage updated. Confidence: 0.6
- Serves customers primarily in India — customer-facing order forms should default the country to India. Confidence: 0.5
- Wants no `dangerouslySetInnerHTML` anywhere in application code — when a library (e.g., next-themes) triggers a React 19 warning about client-rendered script tags, expects a root-cause fix (patch the dependency via pnpm `patchedDependencies`, or use `next/script` with `beforeInteractive`) instead of embedding a raw inline script with `dangerouslySetInnerHTML`. Confidence: 0.6
- For loading states, prefers the App Router `loading.tsx` convention placed next to the route page, reusing the existing shared `Skeleton` component (animate-pulse, `bg-muted`) and mirroring the page's actual layout/grid structure so the skeleton renders in place. Confidence: 0.6
- Prefers new admin modules built on a consistent DB-backed architecture following the existing module's conventions: extend the Prisma schema, then create a data layer under `lib/data-layer/admin/<module>/` (a server `*-data-layer.ts`, a `*-mapper.ts` mapping DB rows to the admin view model, and a client `*-actions.ts` of fetch wrappers), add API routes under `app/api/admin/<module>/`, convert the list/detail pages to async server components with URL-as-source-of-truth, wire the components to the real actions with loading states, and remove all mock data — including downstream consumers (sidebar badge counts, filter dropdowns in sibling tables) — so no placeholder arrays remain. Confidence: 0.7
- When the user points to an existing shared folder of helper functions (e.g., `lib/firebase`) for a feature, reads all the files first to understand the flow, then reuses those functions as-is — never reimplements or modifies code in that shared folder ("don't change any code in this folder just use the functions"). Confidence: 0.7
- Wants media (e.g., image uploads) handled as a commit-time operation: a picked file stays local (with a local preview) until the form is actually submitted, then it's uploaded to storage — so cancelling/closing the form after selecting a file doesn't leave an orphaned upload. Also delete the old image when a record's image is replaced during edit, and delete the image when the record itself is deleted, so storage never accumulates orphaned files. Confidence: 0.8
- Keeps image/media processing server-side (in API routes / server actions) rather than client-side when the utility depends on Node-only libraries (e.g., `sharp`). Confidence: 0.6
- Validates unique-value constraints (e.g., category slug) with a pre-flight check *before* uploading/persisting anything, so a failed save never leaves an orphaned image in storage. Confidence: 0.7
- When a DB create/patch fails after an image upload, performs best-effort cleanup of the just-uploaded orphaned Firebase image; the cleanup must never throw and must not fail the surrounding request. Confidence: 0.8
- Always wraps Firebase storage deletes in try/catch and treats a missing/already-deleted image as success — a missing Firebase object must never fail the DB operation. Confidence: 0.7
- Prefers doing the full image validation (file type, format, size) on the frontend client when a local image is picked, and uploading/deleting images directly from the client component by calling the firebase helpers — no API routes, no FormData, and all server-side image/upload logic removed once the firebase helpers are browser-safe. Confidence: 0.8
